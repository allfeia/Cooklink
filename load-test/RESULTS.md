# Сводный отчёт по нагрузочному и лимитному тестированию

**Прод:** 4 vCPU / 6 ГБ RAM / 3 ГБ swap
**Пайплайн:** metadata → субтитры → LLM → PDF, **без очереди**

Три потолка:
1. при какой интенсивности **падает система**
2. на сколько запросов хватает **лимитов модели** OpenRouter
3. при каком темпе **YouTube отдаёт 429** библиотеке субтитров yt-dlp

Скрипты: `load-test/test1-breakpoint.js` (k6), `load-test/test2-llm-limits.js` (node),
`load-test/test3-youtube-limit.js` (node).

---

## rate limit на gateway (промежуточная)

| область   | что ограничиваем     | лимит        | всплеск | при превышении      |
|-----------|----------------------|--------------|---------|---------------------|
| глобально | создание рецептов    | **20 / мин** | -       | `503 + Retry-After` |
| на IP     | создание рецептов    | **5 / мин**  | 10      | `429 + Retry-After` |
| на IP     | опрос статуса задачи | **60 / мин** | 30      | `429`               |

- Глобальный лимит держит сервер вдали от CPU-стенки: с реальным LLM стенка ≈ 240–360/мин,
  потолок ставим вдвое ниже.
- Числа временные - настоящее решение это **очередь + семафор на воркерах** (следующий
  спринт). Пересмотреть после выката.

## Тест 1 - точка отказа системы

### Методика

- k6 бьёт по `https://cooklink.ru`, нагрузка растёт плоскими ступенями (держим N запр/сек
  минуту-две, потом следующая ступень), executor `ramping-arrival-rate` (держит темп
  независимо от того, как медленно отвечает сервер).
- LLM **замокан** (`LLM_EXTRACT_PATH=/extract-mock`, задержка 4 с) - меряем инфраструктуру.
  Мок не пишет в кэш рецептов, каждый `POST /v1/recipes` реально гоняет metadata +
  субтитры + PDF.

### Прогон 2 CPU / 3 ГБ, без свопа

**Обвал через ~65 с на 1 запр/сек (60/мин).** Не деградация — сразу катастрофа: `POST`
таймаутил на 16–20 с, хост ушёл в OOM (свопа нет), docker-демон завис. Чинили руками:
`systemctl restart docker` + пересборка стека. Из 11006 задач завершилось 14 (0.1%).

**Причина:** нет очереди и лимита параллелизма. Десяток одновременных задач исчерпывает RAM → OOM-killer.

### Прогон 4 CPU / 6 ГБ + 3 ГБ свопа

| ступень | запр/сек | запр/мин  | результат                                                   |
|---------|----------|-----------|-------------------------------------------------------------|
| 1–5     | 1 → 6    | 60 → 360  | держит чисто, 0 отказов сервиса                             |
| **6**   | **8**    | **480**   | **первый обрыв `POST`** - 6 м 41 с от старта, ~889-й запрос |
| 7       | 8 → 10   | 480 → 600 | лавина: 547 обрывов `connection reset` за 90 с              |
| —       | 10       | 600       | k6 сам остановил прогон (предохранитель >35% фейлов create) |

- **Сервис не тормозил.** Латентность `POST`: p95 **295 мс**, max 3.3 с. вплоть до
  обрыва. Он **перестал принимать TCP-соединения**
  (`connection reset by peer` ×513, `unexpected EOF` ×34).
- **Прод восстановился сам**. health 200 за ~400 мс сразу после теста.
- По Grafana (node-exporter, окно 16:13-16:16): **все 4 ядра в 100%** в момент обрывов.
  Память до ~6 ГБ, чуть ушло в swap и вернулось - **OOM не было**. 

### Вывод по тесту 1

| параметр             | 2 CPU / 3 ГБ, без свопа             | 4 CPU / 6 ГБ + своп                  |
|----------------------|-------------------------------------|--------------------------------------|
| держит без сбоев     | ~1 запр/сек                         | **6 запр/сек (360/мин)**             |
| первый отказ сервиса | ~1 запр/сек                         | **8 запр/сек (480/мин)**             |
| полный отказ         | ~1–2 запр/сек                       | 10 запр/сек (600/мин)                |
| характер отказа      | OOM, зависание демона, ручной ребут | обрыв соединений, самовосстановление |
| что упирается        | RAM (нет свопа)                     | **CPU (4 ядра в 100%)**              |

- Апгрейд х2 CPU + х2 RAM + своп → потолок вырос в ~5 раз, отказ стал управляемым.
- **С реальным LLM потолок ниже** - задачи живут в 3–5 раз дольше. Оценочно
  **4–6 запр/сек (240–360/мин)**.
- **Добавлять ресурсы не нужно.** 8 запр/сек ≈ 480 задач/мин ≈ 690 тыс/сутки

## Тест 2 - лимиты модели (OpenRouter, `meta-llama/llama-3.3-70b-instruct`)

### Методика

- node-скрипт бьёт **напрямую в OpenRouter** тем же клиентом и промптом, что
  `llmService.ts` (та же system-инструкция, `temperature 0.2`, `max_tokens 2048`).
  Прод и YouTube не трогает.
- Вход — 87 реальных транскриптов из `backend/external_services_tests/subtitles/*.txt`.
- По каждому запросу: латентность, токены in/out, `finish_reason`, валидна ли схема JSON.
  На ошибке — HTTP-статус, `retry-after`, флаг 429/402. `/auth/key` до и после → факт.
  стоимость.
- Ключ: **free-tier, кредитов $0**, usage копится «в минус».

### Прогоны

| прогон | concurrency | запросов | лимит (429/402) | стоимость | латентность p95 / max |
|--------|-------------|----------|-----------------|-----------|-----------------------|
| A      | 2           | 60       | **не пойман**   | $0.0205   | 69 с / 84 с           |
| B      | 20          | 120      | **не пойман**   | $0.0275   | 87 с / 104 с          |

За день **180 реальных запросов**, всплески до ~96/мин и 20 параллельных, баланс $0 →
**OpenRouter ни разу не вернул 429 или 402.** Под нагрузкой не отклоняет, а ставит в
очередь и замедляет (p95 69 → 87 с).

### Сколько рецептов ещё хватит бесплатно

Free-tier OpenRouter даёт лимит расхода **чуть меньше $1**, прежде чем потребуется оплата.
Грант и промо тратятся раньше купленных кредитов.

**Проверка ключа 10 сентября 2026** (`/auth/key`, `/credits`):

```
usage         = $0.1010
total_credits = $0
is_free_tier  = true
limit         = null
```

|                                 |                                                                                       |
|---------------------------------|---------------------------------------------------------------------------------------|
| израсходовано из ~$1            | **$0.101** (~300 рецептов)                                                            |
| осталось бесплатно              | **≈ $0.90**                                                                           |
| стоимость рецепта               | $0.00027–0.00034 (замер: $0.048 / 180; в проде транскрипты длиннее → верхняя граница) |
| **осталось рецептов бесплатно** | **≈ 2 600–3 300**, затем HTTP 402 (не бан, обратимо)                                  |
| пополнение $10                  | ≈ ещё ~30 000 рецептов                                                                |

### Вывод по тесту 2

- Жёсткого лимита по запросам/сутки (≥180), по частоте (≥96/мин) или блокировки при $0
  кредитов **не найдено**.
- Нельзя исключить более высокий суточный или $-лимит, до которого не дошли.

## Тест 3 - 429 от YouTube (yt-dlp / субтитры)

### Методика

- Изолированный скрипт на **прод-сервере**, в разовом контейнере из образа воркера
  (`docker compose run --rm --no-deps metadata-worker`) - та же версия yt-dlp, **тот же
  файл кук, что использует сервис** (`/app/youtube_cookies.txt`).
- Вызов 1:1 с `videoMetadataService.ts`: `dumpSingleJson` + `skipDownload` + куки.
  **1 вызов yt-dlp = 1 запрос** в скрипте.
- Классификатор: `429` (`HTTP Error 429`) vs `err` (приватное/удалённое
  видео и пр.) vs `ok`.

### Прогон 10 сентября 2026 - ~100 запросов/мин

```
время         : 7:07
запросов      : 707   (~99/мин)
ok / 429 / err: 489 / 2 / 213
доля 429      : 0.3%
первый 429    : запрос #542, время 5:29
оценка ротации: ~1 раз в 354 запроса
```
