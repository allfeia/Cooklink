# Нагрузочное тестирование — результаты

Дата: 4–8 сентября 2026. Цель — найти три потолка:
1. при какой интенсивности запросов **падает сама система** (CPU/RAM/соединения);
2. на каком запросе **YouTube даёт 429** библиотеке субтитров (yt-dlp);
3. на сколько запросов **хватает лимитов модели** (OpenRouter).

Инструменты: `load-test/test1-breakpoint.js` (k6, вся система, LLM замокан),
`load-test/test2-llm-limits.js` (node, только модель, напрямую в OpenRouter).

---

## Тест 1 — точка отказа системы

### Методика

- k6 бьёт по `https://cooklink.ru`, нагрузка растёт плоскими ступенями (держим N запр/сек
  минуту-две, потом следующая ступень).
- LLM **замокан** (`LLM_EXTRACT_PATH=/extract-mock`, задержка 4 с) — чтобы не упираться в
  модель и мерить именно инфраструктуру. Мок не пишет в кэш рецептов → каждый `POST`
  реально гоняет metadata + субтитры + PDF.
- Корпус — 100 разных кулинарных видео, обход по кругу.
- Каждый запрос: `POST /v1/recipes` → поллинг статуса каждые 3 с до `completed`/`failed`.

### Прогон 1 — сервер 2 CPU / 3 ГБ, без свопа

| ступень | запр/сек | запр/мин |
|---|---|---|
| 1 | 1 | 60 |
| … | до 25 | до 1500 |

**Обвал через ~65 секунд, на 1 запр/сек (60/мин).** Не деградация — сразу катастрофа:
`POST` таймаутил на 16–20 с, весь хост ушёл в OOM (память кончилась, свопа нет),
docker-демон завис. Чинили руками: `systemctl restart docker` + пересборка всего стека.
Из 11006 созданных задач завершилось **14 (0.1%)**.

**Причина:** нет очереди и лимита параллелизма на fan-out к yt-dlp (2 процесса на задачу)
+ Gotenberg (Chromium). На маленькой машине без свопа десяток одновременных задач
исчерпывает RAM → kernel OOM-killer.

### Прогон 2 — сервер 4 CPU / 6 ГБ + 3 ГБ свопа

| ступень | запр/сек | запр/мин | результат |
|---|---|---|---|
| 1–5 | 1 → 6 | 60 → 360 | держит чисто, 0 отказов сервиса |
| **6** | **8** | **480** | **первый обрыв `POST`** — 6 мин 41 с от старта, ~889-й запрос |
| 7 | 8 → 10 | 480 → 600 | лавина: 547 обрывов `connection reset` за 90 с |
| — | 10 | 600 | k6 сам остановил прогон (предохранитель: >35% фейлов create) |

- **Сервис не тормозил.** Латентность `POST /v1/recipes` — p95 **295 мс**, max 3.3 с —
  вплоть до обрыва. Он не отвечал медленно, а **перестал принимать TCP-соединения**
  (`connection reset by peer` ×513, `unexpected EOF` ×34).
- **Прод восстановился сам** — health 200 за ~400 мс сразу после теста, без вмешательства.
- По Grafana (node-exporter, окно 16:13–16:16): **CPU всех 4 ядер встал в 100%** ровно в
  момент обрывов. Память заполнилась до ~6 ГБ, **чуть ушло в своп и вернулось** — OOM не
  было. Узкое место — **CPU** от массового спавна процессов yt-dlp (Python) + Chromium.
- Побочно: диск root на **90%** — прогон нагенерил логов; перед следующими тестами чистить.

### Вывод по тесту 1

| параметр | 2 CPU / 3 ГБ, без свопа | 4 CPU / 6 ГБ + своп |
|---|---|---|
| держит без сбоев | ~1 запр/сек | **6 запр/сек (360/мин)** |
| первый отказ сервиса | ~1 запр/сек | **8 запр/сек (480/мин)** |
| полный отказ | ~1–2 запр/сек | 10 запр/сек (600/мин) |
| характер отказа | OOM, зависание демона, ручной ребут | обрыв соединений, самовосстановление |
| что упирается | RAM (нет свопа) | **CPU (4 ядра в 100%)** |

- Апгрейд ×2 CPU + ×2 RAM + своп → потолок вырос в ~5 раз и отказ стал управляемым.
- **С реальным LLM потолок ниже** — задачи живут в 3–5 раз дольше, держат ресурсы. Оценочно
  **4–6 запр/сек (240–360/мин)**.
- Стенка резкая (сервер не деградирует плавно, а разом отказывает) — это следствие
  отсутствия очереди/лимита параллелизма, а не нехватки железа.
- **Добавлять ресурсы сейчас не нужно.** 8 запр/сек ≈ 480 задач/мин ≈ 690 тыс/сутки — для
  B2B-нагрузки запас огромный. Лечить архитектурой (очередь + семафор на воркеры).

## Тест 1, побочно — лимит YouTube (429 на субтитры)

- **Первый 429 от YouTube — на 2-м запросе**, через ~24 секунды, на 1 запр/сек. В обоих
  прогонах одинаково.
- Всю дорогу, на любом rps: metadata `VIDEO_UNAVAILABLE` ×248 + субтитры 429 ×154 +
  `NO_SUBTITLES` ×24. Из ~481 задачи, что получили `job_id`, завершилось **55 (11%)** — и
  часть из них это кэш-хиты (мгновенные, без обращения к YouTube).
- **Это не «сколько запросов до 429», а «IP перегружен по частоте».** Каждая задача = 2
  вызова yt-dlp (metadata + субтитры) + до ×3 ретраев. Даже 1 задача/сек = ~2–6 вызовов
  yt-dlp/сек ≈ 120–360/мин — мгновенно за порогом YouTube.
- **Обычный редкий трафик (запрос раз в минуты) лимит не задевает** — это подтверждается
  в проде. Проблема появляется только на всплеске.
- Устойчивый потолок с **одного IP без прокси** — где-то **< 1 задачи/сек**. Точнее не
  мерили: каждый прогон жжёт IP на часы.
- После жёсткого теста живые запросы падают на субтитрах несколько часов, пока IP остывает.

**Лечить:** семафор на параллельные вызовы yt-dlp (не долбить YouTube пачками), не
ретраить агрессивно в 429 (откладывать в очередь), для роста — резидентные прокси с
ротацией.

## Тест 2 — лимиты модели (OpenRouter, llama-3.3-70b-instruct)

### Методика

- node-скрипт бьёт **напрямую в OpenRouter** тем же клиентом и промптом, что `llmService.ts`
  (та же system-инструкция, `temperature 0.2`, `max_tokens 2048`). Прод и YouTube не трогает.
- Вход — 87 реальных транскриптов из `backend/external_services_tests/subtitles/*.txt`,
  разной длины.
- По каждому запросу: латентность, токены in/out (из `usage`), `finish_reason`, парсится
  ли ответ в валидный по схеме JSON. На ошибке — HTTP-статус, `retry-after`, флаг 429/402.
- `/auth/key` до и после → фактическая стоимость по дельте `usage`.
- Состояние ключа: **free-tier, кредитов $0**, usage накапливается «в минус».

### Прогон 1 — concurrency 2, 60 запросов

| | |
|---|---|
| Успешно | **60 / 60** |
| Первый лимит (429/402) | **не пойман** |
| Стоимость | $0.0205 ($0.00034/запрос) |
| Токены | вход ~1300/запрос (до 5300), выход ~500–750 на реальном рецепте |
| `finish_reason` | везде `stop` — ответы не обрезаются, 2048 токенов хватает |
| Валидная схема | 65% |
| Латентность | p50 9.3 с, p95 **69 с**, max **84 с** |

Реальная частота была всего ~11 запр/мин (запросы по 5–80 с) — под любым RPM-лимитом прошли.

### Прогон 2 — concurrency 20, 120 запросов

| | |
|---|---|
| Успешно | **120 / 120** |
| Первый лимит (429/402) | **не пойман** |
| Стоимость | $0.0275 |
| Валидная схема | 60% |
| Латентность | p50 7.9 с, p95 **87 с**, max **104 с** |
| Пиковая частота | ~96 запр/мин на старте бёрста |

OpenRouter **не отклонял** бёрст, а **ставил в очередь и замедлял** — при concurrency 20
p95 вырос 69 → 87 с, max до 104 с.

### Вывод по тесту 2 (оба прогона суммарно)

За день: **180 реальных запросов к модели** (60 + 120) + служебные пробы, бёрсты до
~96 запр/мин и 20 параллельных, баланс $0 — **OpenRouter ни разу не вернул 429 или 402**.

| вопрос | ответ |
|---|---|
| жёсткий лимит по запросам/сутки | **не найден** (≥180/сутки без отказа) |
| лимит по частоте (RPM) | **не найден** (≥96 запр/мин без 429) |
| блокировка при $0 кредитов | **нет** — аккаунт крутит платную модель в минус |
| «на сколько хватает токенов» | по деньгам — на **тысячи**: $1 ≈ 3000 рецептов, $10 ≈ 30 000 |
| реальный «лимит» модели | **латентность**: под нагрузкой время растёт до 90–100 с/запрос |
| качество | 60–65% валидной схемы; «невалидные» — в основном корректные «рецепта в видео нет» (шортсы) + ~1–2% сбоев API (`in=0, finish=error`) |

- Предположение «~50 запросов/сутки free-tier» — **опровергнуто**. Такого потолка нет
  (по крайней мере ≤180/сутки, ≤96/мин).
- Нельзя исключить более высокий суточный лимит или $-лимит, до которого мы не дошли, и
  что OpenRouter пометит аккаунт позже. Но в наблюдаемом диапазоне лимита нет.
- Настоящее ограничение — **скорость**. Реальное извлечение рецепта: **15–25 с типично, до
  84–104 с в хвосте**, только модель. Плюс metadata + субтитры + PDF → полный пайплайн
  **20–30 с обычно, 90+ с в худшем случае**. USER_GUIDE обещает «10–40 сек» — хвост длиннее.
- Стоимость — не ограничение. 180 рецептов = $0.048. Пополнения на $10 хватит на ~30 тыс.

## Итоговые выводы

| | что нашли | что делать |
|---|---|---|
| **Сервис** | падает на ~8 запр/сек (480/мин), CPU 100%; с реальным LLM ~4–6 запр/сек. Отказ резкий. | Не железо. Очередь + лимит параллелизма воркеров. Своп оставить. |

| **Модель / OpenRouter** | жёсткого лимита по запросам/частоте/кредитам не найдено (≥180/сут, ≥96/мин, баланс $0). Ограничение — латентность (до 100 с/запрос под нагрузкой). Стоимость ничтожна. | Пополнить OpenRouter на $10 (снимет риск и даст запас). Поднять `max_tokens`? — нет, `finish=stop` везде. Следить за долей валидной схемы (65%). |

**Приоритет проблем:** 1) доступ к YouTube (упираемся раньше всего), 2) очередь/параллелизм
